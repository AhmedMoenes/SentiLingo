PART 4

4. Database Design

A minimal experiment and model registry that preserves reproducibility without turning the five-week capstone into a database product.

4.1 Decision and Scope

Selected option. SentiLingo will use a small, vendor-neutral relational design to record dataset versions, experiment runs, metrics and generated artefacts. SQLite is the preferred implementation if persistence is added because it is local, zero-cost and easy to back up. The logical design remains portable to PostgreSQL or SQL Server.

The registry answers four practical questions: Which data produced a result? Which configuration was executed? How did it perform for each supported language? Which files belong to that run? It does not store user accounts, raw customer messages or prediction history.

StoredReferenced, not copiedDeliberately excluded
Dataset version metadata and checksumsSource manifests and split filesUser accounts, passwords, roles and sessions
Run configuration, seed, environment and timingModel weights, tokenizers and reportsRaw customer text and personal data

4.4 Relationships and Integrity Rules

  1. A dataset version may have many experiment runs; every run must reference exactly one dataset version.
  2. A run may have many metric and artefact records. Orphan records are rejected by foreign keys.
  3. Completed runs are append-only audit evidence. Corrections create a new run; identifiers and historical metrics are not overwritten.
  4. The tuple of run, split, language scope, label scope and metric name is unique.
  5. Counts, durations, sizes and metric values cannot be negative. Status and scope fields use controlled values.
  6. Only a model artefact may be marked selected, and at most one model is selected for the current local-demo release.
  7. Test metrics are written only after the configuration is locked. This is enforced by the experiment workflow and reviewed evidence.

4.6 Privacy, Security and Retention

  • Data minimisation: store experiment metadata, not raw feedback or user identifiers.
  • Prediction logging: disabled by default. The Streamlit application processes text in memory and does not add it to the registry.
  • Secrets: never store tokens, passwords or cloud keys in the database or repository.
  • Access: the local registry is writable only by the project team. Submission exports are read-only CSV or JSON files.
  • Retention: keep completed-run metadata and checksums for reproducibility; delete unneeded model binaries separately without deleting their historical records.
  • Backup: copy the SQLite file and exported registry at each milestone and before the presentation.

4.7 Physical Design and Portability

SQLite is the default physical store because the demonstration is local and concurrent writes are not expected. Foreign keys must be enabled. Timestamps use UTC ISO 8601 values, identifiers are text-based and JSON content carries an explicit schema version.

Physical choiceDecision
IndexesIndex runs by dataset and status, metrics by run and scope, and artefacts by run and type.
Generated filesThe database and model artefacts are generated outputs and are not committed; schema documentation and export examples are committed.
Backup and exportUse a copied database file plus CSV or JSON exports so evaluators are not forced to install SQLite tools.
Migration pathKeep generic types and application-level JSON validation so PostgreSQL or SQL Server can replace SQLite later.

4.8 Alternatives and Consequences

AlternativeWhy it was not selectedConsequence of skipping it
No operational databaseConfiguration files alone are simple but make cross-run comparison, integrity rules and audit queries harder.The team accepts a small persistence task to gain database-design and reproducibility experience.
Full application databaseAccounts, roles, authentication, prediction history and analytics would consume time needed for data quality and modelling.The demo is single-team and local; it will not provide sign-in, personal history or multi-user concurrency.
Cloud-managed databaseIt adds cost, credentials, networking and availability risks without helping the required offline demonstration.The first release does not demonstrate cloud database operations; portability is preserved in the logical design.
Store model binaries in the databaseLarge binary objects complicate backup, transfer and version control.File storage must be organised and protected; the registry stores URIs, checksums and metadata instead.

4.9 Acceptance Checklist

  • The ER model and all four tables are reviewed by the team.
  • Primary keys, foreign keys, controlled values and unique metric scope are documented.
  • No raw feedback, credentials or prediction history are included.
  • One sample run can be traced to its dataset, metrics and artefacts.
  • SQLite backup and CSV or JSON export can be demonstrated if persistence is implemented.
